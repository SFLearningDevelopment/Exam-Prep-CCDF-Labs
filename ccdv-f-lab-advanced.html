Build and ship an agent

Orientation

The release assistant becomes an agent. Given a repository and a date range, it plans its own steps, gathers pull requests, classifies each change, drafts notes, checks them against a style guide, and hands back a result with a trace of what it did.

The distinction that matters: a workflow is a path you wrote, and an agent chooses its own path. You give up predictability and gain the ability to handle inputs you did not anticipate. Everything else in this lab exists to buy back some of the predictability you traded away.

Glossary

Workflow vs agent
A workflow has fixed steps with the model filling gaps. An agent decides its own sequence and stopping point. Prefer a workflow whenever the steps are actually known.
Orchestrator-worker
One agent plans and delegates to subagents, each with its own context window and narrower toolset, then assembles their outputs.
Subagent
A separate agent invocation with its own context. Its intermediate work never enters the orchestrator's window, which is the main reason to use one.
Compaction
Summarising earlier turns so a long-running agent stays inside its context window without losing the thread.
Hook
Code that runs at a fixed point in the loop — before or after a tool call — and can block it. Deterministic, unlike an instruction the model may weigh against other instructions.
Verify

The Agent SDK, Claude Code configuration and hook event names change with releases. Confirm current package names, settings file locations and event names in the documentation before following stages 3 and 5 literally.

1

Decide whether you need an agent at all

Writing. The cheapest stage and the one most often skipped.

Write down the steps your release-notes task requires. If you can write them all, you have a workflow, and a workflow is cheaper, faster, testable and debuggable.

PatternShapeUse when
Single callOne prompt, one responseThe task fits in one step
ChainOutput of one call feeds the nextSteps are known and always in the same order
RoutingClassify first, then dispatch to a specialised pathInput kinds differ and each needs different handling
ParallelFan out independent calls, then mergeSubtasks do not depend on each other
Orchestrator-workerA planner delegates to subagentsThe number and nature of subtasks depend on the input
Autonomous loopModel decides each next step until doneThe path genuinely cannot be known in advance

For release notes, most of it is a chain: gather, classify, draft, check. Only classification of an unknown number of changes benefits from delegation. So the honest design is a workflow with one agentic segment — which is what you will build.

Exam lens

Scenario questions describe a task and expect the simplest sufficient pattern. Fixed known steps means a chain, and answering "agent" there is over-engineering — a distractor that appears often. The trigger for a real agent is that the number or order of steps depends on input the developer cannot see in advance. Also know the cost shape: agents multiply calls, so an agentic design needs a step ceiling and a token budget before it ships.

Build the agent loop by hand

Code. Extend Lab 2's loop with a plan, a budget and a trace.

The Lab 2 loop already runs until the model stops calling tools. An agent adds three things: an explicit plan, resource limits, and a record of what happened.

agent.py

class Agent:
    def __init__(self, tools, registry, model="claude-sonnet-4-6",
                 max_steps=12, token_budget=120_000):
        self.tools, self.registry = tools, registry
        self.model, self.max_steps, self.token_budget = model, max_steps, token_budget

    def run(self, task, system):
        messages = [{"role": "user", "content": task}]
        trace, spent = [], 0

        for step in range(self.max_steps):
            resp = client.messages.create(
                model=self.model, max_tokens=4096, system=system,
                tools=self.tools, messages=messages,
            )
            spent += resp.usage.input_tokens + resp.usage.output_tokens
            trace.append({"step": step, "stop": resp.stop_reason,
                          "tools": [b.name for b in resp.content if b.type == "tool_use"],
                          "tokens": spent})

            if spent > self.token_budget:
                return {"status": "budget_exceeded", "trace": trace}
            if resp.stop_reason != "tool_use":
                text = "".join(b.text for b in resp.content if b.type == "text")
                return {"status": "done", "output": text, "trace": trace}

            messages.append({"role": "assistant", "content": resp.content})
            messages.append({"role": "user", "content": self._execute(resp.content)})

        return {"status": "step_limit", "trace": trace}

Three termination conditions, all explicit: the model finished, the step ceiling hit, the token budget hit. An agent with only the first is an agent that can run until your card declines.

The system prompt does the planning work:

SYSTEM = '''You produce release notes for a repository over a date range.

Work in this order: gather merged pull requests, classify each as feature, fix
or chore and flag breaking changes, then draft the notes.

Rules:
- Call list_merged_prs exactly once per repository and date range. Do not re-fetch.
- If the range returns more than 40 pull requests, classify in batches.
- If a pull request title is ambiguous, call get_issue rather than guessing.
- Stop and report when the draft is written. Do not post it.'''
Exam lens

Agent-construction questions look for the guards. A loop with no step ceiling, no token budget and no failure path is the wrong answer regardless of how good its prompt is. Know that a plan stated in the system prompt is guidance the model can deviate from, whereas a step ceiling in your code is a limit it cannot — which is the same distinction that separates hooks from instructions in stage 5.

3

Delegate to subagents

Code. Isolation of context is the real gain.

Classifying forty pull requests in the main loop puts forty tool results in one window. Delegating gives each batch its own context, and only the classification comes back.

def classify_batch(prs):
    '''Runs as a separate invocation with its own context window.'''
    resp = client.messages.create(
        model="claude-haiku-4-5",             # cheaper model, narrower task
        max_tokens=2048,
        system="Classify each pull request as feature, fix or chore. Flag breaking changes.",
        tools=[CLASSIFY_TOOL],
        tool_choice={"type": "tool", "name": "emit_classification"},
        messages=[{"role": "user", "content": json.dumps(prs)}],
    )
    return next(b.input for b in resp.content if b.type == "tool_use")["items"]

def classify_all(prs, size=20):
    out = []
    for i in range(0, len(prs), size):
        out.extend(classify_batch(prs[i:i + size]))
    return out                                 # only results reach the orchestrator

Two things happened at once. The orchestrator's context stayed small because intermediate reasoning never entered it. And the subtask ran on a cheaper model, because classification against a fixed schema does not need the orchestrator's capability.

The Agent SDK provides this shape — subagents, permissions, hooks and session handling — without hand-rolling it:

pip install claude-agent-sdk
from claude_agent_sdk import query

async for message in query(
    prompt="Draft release notes for sourcefuse/api since 2026-08-01",
    options={"allowed_tools": ["Read", "Grep"], "permission_mode": "acceptEdits"},
):
    print(message)

Build one segment both ways. Hand-rolled teaches the mechanics; the SDK is what you would ship.

Verify

Agent SDK package name, function signature and option names differ across versions. Check the current API before copying this call.

Exam lens

The reason to reach for a subagent is context isolation, not parallelism — that is the distinction most often tested. Related: model tiering per subtask, where the orchestrator is the capable model and workers are cheap, is the standard cost answer for a multi-step agent. And a subagent starts with a fresh window, so anything it needs must be passed in explicitly; assuming it inherits the parent conversation is a common wrong answer.

4

Keep memory across a long task

Code. Compaction, and what to keep outside the window.

A long-running agent hits the context window. Three responses, and they are not alternatives — a real system uses all three.

  1. Compact. When context passes a threshold, summarise the older half and replace it, keeping the system prompt and the most recent turns verbatim.
  2. Externalise. Write durable facts to a file or store, and let the agent read them back with a tool. The window holds a pointer; the store holds the content.
  3. Scope. Give each subagent only what its task needs, so the big window is needed less often.
def compact(messages, keep_recent=6):
    head, tail = messages[:-keep_recent], messages[-keep_recent:]
    if len(head) < 4:
        return messages

    summary = client.messages.create(
        model="claude-haiku-4-5", max_tokens=1024,
        system="Summarise this agent transcript. Keep decisions, findings and open "
               "questions. Drop tool payloads and restated instructions.",
        messages=[{"role": "user", "content": json.dumps(_serialise(head))[:60000]}],
    ).content[0].text

    return [{"role": "user", "content": f"Summary of earlier work:\n{summary}"}] + tail

Call it when count_tokens crosses a threshold rather than on a turn count, since one verbose tool result can consume more than ten short turns.

Externalising is often better. Have the agent write findings to notes.json through a tool and read them back when needed — durable across runs, and no summarisation loss.

What compaction costs

Summarising is lossy and irreversible. Detail dropped at step 20 is gone at step 40, and the agent will not know it is missing. Keep decisions and constraints verbatim; summarise narration.

Exam lens

Context-window questions have a decision order: reduce what enters the window, then externalise, then compact — compaction last because it loses information. A scenario where an agent "forgets a constraint given at the start" points at compaction dropping it, and the fix is pinning that constraint in the system prompt where compaction cannot reach it.

5

Enforce rules with hooks, not requests

Code plus configuration. Where safety stops being advisory.

"Never post without confirmation" in a system prompt is an instruction weighed against other instructions. A hook is code that runs before the tool call and can refuse it.

In your own loop, that is a check in the executor:

BLOCKED = {"post_draft": lambda args: not args.get("confirmed"),
           "delete_release": lambda args: True}

def guard(name, args):
    check = BLOCKED.get(name)
    if check and check(args):
        return {"allowed": False, "reason": f"{name} requires explicit confirmation"}
    return {"allowed": True}

Refused calls come back as a tool_result with is_error, so the agent learns it was blocked and can ask rather than failing opaquely.

In Claude Code the same idea is configuration. A PreToolUse hook receives the pending call and can block it; a PostToolUse hook runs after — formatting, linting, audit logging. Hooks live in settings alongside permissions, and CLAUDE.md carries project conventions into every session.

Try it: add a PreToolUse hook that blocks writes to .env, then ask Claude Code to edit that file and watch the refusal.

MechanismEnforcementRight for
System promptAdvisoryTone, style, preferred approach
Tool schemaStructuralShape and type of arguments
Permissions / allowed toolsHardWhich tools exist for this session at all
HookHard, conditionalRules depending on arguments or state
Exam lens

The advisory-versus-enforced split answers most safety questions. Anything that must never happen belongs in a hook or a permission, not in a prompt. Know the two hook positions — before a tool call, where blocking is possible, and after, where it is not — and that Claude Code sits in the exam at a small weight, so recognising CLAUDE.md, settings-based permissions, hooks and headless mode is enough.

6

Evaluate the agent, not just the output

Code. Multi-step systems fail in ways a final-answer check misses.

An agent can produce a good answer having taken six wrong turns, and produce a bad one from a correct plan. Score both.

eval_agent.py

CASES = [
    {"task": "Release notes for sourcefuse/api, 2026-08-01 to 2026-08-31",
     "expect_tools": ["list_merged_prs"], "forbid_tools": ["post_draft"],
     "must_contain": ["breaking"]},
    {"task": "Release notes for a repository I do not have access to",
     "expect_tools": [], "forbid_tools": ["list_merged_prs"], "must_contain": ["not permitted"]},
]

def score(case):
    r = agent.run(case["task"], SYSTEM)
    used = {t for step in r["trace"] for t in step["tools"]}
    return {
        "completed":  r["status"] == "done",
        "tools_ok":   set(case["expect_tools"]) <= used and not (set(case["forbid_tools"]) & used),
        "content_ok": all(s in (r.get("output") or "").lower() for s in case["must_contain"]),
        "steps":      len(r["trace"]),
        "tokens":     r["trace"][-1]["tokens"] if r["trace"] else 0,
    }

Four dimensions, and they move independently. Completion says it terminated. Tool correctness says it took a defensible path. Content says the answer is right. Steps and tokens say what it cost — a change that improves quality while doubling steps may not be an improvement.

For open-ended quality, a judge model scores drafts against your style guide. Use it for prose, not for questions a set comparison answers.

Run the harness on every prompt or schema change and keep the numbers. This is the artefact that lets you say a change was an improvement rather than a preference.

Exam lens

Evaluation questions test layering. Deterministic assertions for anything checkable — which tools, which arguments, whether a forbidden action occurred. Judge models for open-ended text only. Cost and step counts tracked alongside quality, because an agent that gets better and triples its spend has traded, not improved. And the negative case is the one that catches an over-eager agent, which is why every suite needs one.

7

Ship it

Configuration and operations. The last domain, and the one that decides whether any of this survives.

Configuration

Nothing that varies between environments belongs in code: model IDs, budgets, timeouts, allow-lists, prompt versions.

from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    anthropic_api_key: str                 # from env, never a default
    model_orchestrator: str = "claude-sonnet-4-6"
    model_worker: str = "claude-haiku-4-5"
    max_steps: int = 12
    token_budget: int = 120_000
    allowed_repos: list[str] = []
    prompt_version: str = "v3"

    class Config:
        env_file = ".env"

Version your prompts alongside code and record prompt_version in every log line. When quality moves, that field tells you which change to look at.

Secrets

Keys come from the environment in development and a secret manager in production. Rotate on a schedule and immediately after any suspected exposure. One key per environment and per service, so revoking one does not take down everything. Nothing calls the API directly from a browser or mobile client.

Observability

One structured line per agent run, and one per step: run id, prompt version, model, step count, tools used, tokens in and out, latency, terminal status. Alert on the ratio of step_limit and budget_exceeded outcomes rather than on individual failures.

Degradation

FailureBehaviour
Rate limitedBackoff with jitter; queue rather than drop
OverloadedRetry; fall back to a smaller model if the task allows
Budget exceededReturn partial work with a clear status, never silence
Tool unavailableReturn is_error so the agent can adapt
Bad outputValidate against the schema and retry once, then escalate

Deploy the release-notes agent behind a small HTTP endpoint that takes a repository and a date range and returns the draft with its trace. Run your Lab 3 harness against the deployed endpoint rather than the local function — that is the difference between testing your code and testing your system.

Exam lens

Lifecycle questions expect production hygiene: configuration external to code, prompts versioned and logged with outputs, secrets in a manager with rotation, structured logs per run, and explicit degradation. The recurring distractor is an answer that improves the prompt or the model when the described problem is operational — a system with no run logs cannot be debugged by better prompting.
