Call Claude properly

Build a release-notes assistant on the Messages API: system prompts, multi-turn state, streaming, schema-forced output, token accounting, model choice on evidence, and the failures that only appear in production.

Orientation

You are building a release-notes assistant: it takes a list of merged pull request titles and produces a short, structured summary that a product manager can paste into a changelog. Small enough to finish, real enough to expose every mechanic the exam tests.

By the end you will have made a call, streamed one, forced the output into a schema you can trust, measured what each call costs, chosen a model on evidence rather than habit, and handled the errors that show up in production rather than in tutorials.

Glossary

Messages API
The single endpoint for text generation. It is stateless: a multi-turn conversation exists only because you resend the whole message list every time.
System prompt
A top-level system parameter, not a message with role: "system". It sets role and rules for the whole exchange.
Content block
Responses are a list of typed blocks, not a string. A plain answer is one text block; tool use, images and extended thinking add other types.
stop_reason
Why generation ended: end_turn for a natural finish, max_tokens for truncation, stop_sequence, or tool_use. Your code should branch on it.
Prompt caching
Marking a stable prefix with cache_control so repeated calls reuse it at a lower rate. Requires a minimum prefix length and expires after a short idle window.
On API keys and cost

These labs call a real API and spend real money. Budget a few US dollars for the three labs if you keep to the small models where the lab says so.

Create a key at the Anthropic Console under API keys, put it in a workspace with a spend limit, and export it as ANTHROPIC_API_KEY. The SDK reads that variable, so no key ever appears in your code.

Use a personal key for now. If SourceFuse issues scoped workspace keys for training later, only the export line changes.

Verify

Model names, pricing and context limits change often. Every model ID here is an example. Confirm the current list in the Anthropic docs or with client.models.list() and use what you find.

Set up and make one call

Terminal. Get a response back before anything else.

Create a project, install the SDK, and put your key in the environment rather than the code.

mkdir claude-release-notes && cd claude-release-notes
python3 -m venv .venv && source .venv/bin/activate
pip install anthropic

export ANTHROPIC_API_KEY="sk-ant-..."     # add to ~/.zshrc or use a .env file
echo ".venv/\n.env" > .gitignore

first_call.py

from anthropic import Anthropic

client = Anthropic()          # reads ANTHROPIC_API_KEY from the environment

resp = client.messages.create(
    model="claude-haiku-4-5",
    max_tokens=512,
    system="You write concise release notes for a developer audience.",
    messages=[
        {"role": "user", "content": "Summarise: 'fix: retry on 429', 'feat: add CSV export'"}
    ],
)

print(resp.content[0].text)
print(resp.stop_reason, resp.usage.input_tokens, resp.usage.output_tokens)

Three details in that call are exam material. max_tokens is required and caps only the output. system is a top-level parameter — there is no system role inside messages. And resp.content is a list of blocks, so content[0].text works now but breaks the moment tools or thinking blocks appear.

The TypeScript shape is the same:

A running spend meter

Before going further, build the thing that tells you what every call costs. You will use it in all three labs.

cost.py

'''Running spend meter. Import this in every lab script.'''

# USD per million tokens. Verify against the current price sheet before trusting.
PRICES = {
    "claude-haiku-4-5": (1.00, 5.00),
    "claude-sonnet-5":  (2.00, 10.00),
    "claude-opus-5":    (5.00, 25.00),
}
CACHE_WRITE_MULT = 1.25      # 5-minute cache write
CACHE_READ_MULT  = 0.10      # cache hit

_session_total = 0.0
_calls = 0

def record(model, usage, label=""):
    global _session_total, _calls
    base_in, base_out = PRICES.get(model, (2.00, 10.00))

    cache_w = getattr(usage, "cache_creation_input_tokens", 0) or 0
    cache_r = getattr(usage, "cache_read_input_tokens", 0) or 0

    cost = (
        usage.input_tokens  * base_in
        + usage.output_tokens * base_out
        + cache_w * base_in * CACHE_WRITE_MULT
        + cache_r * base_in * CACHE_READ_MULT
    ) / 1_000_000

    _session_total += cost
    _calls += 1
    print(f"[spend] {label or model:28} "
          f"in={usage.input_tokens:6} out={usage.output_tokens:5} "
          f"cache_r={cache_r:6} "
          f"${cost:.5f}  |  session ${_session_total:.4f} over {_calls} calls")
    return cost

def total():
    return _session_total

Now wrap every call so you never make one without seeing its price:

from anthropic import Anthropic
import cost

client = Anthropic()

def call(label="", **kwargs):
    resp = client.messages.create(**kwargs)
    cost.record(kwargs["model"], resp.usage, label)
    return resp

Use call(...) in place of client.messages.create(...) from here on. Every lab script in this course assumes it exists. At the end of a session, cost.total() tells you what the session cost, and the Console's usage page tells you what it actually billed — compare the two once, so you trust the meter.

Keep the bill small

Three habits do most of the work. Default to Haiku and only move up when a task demonstrably fails on it. Set max_tokens to what the answer actually needs rather than a round number. And use count_tokens, which costs nothing, to check a prompt before sending it.

Exam lens

A frequent distractor puts the system prompt in the messages array as {"role": "system", ...}. That is the OpenAI shape, not Anthropic's, and it fails validation. Equally common: treating max_tokens as a budget for the whole request rather than the completion, or forgetting it is mandatory.

Hold a conversation the model cannot remember

Code. The API is stateless; multi-turn is something you build.

There is no session on the server. A conversation is a list you keep and resend, and its length is what you pay for on every turn.

chat.py

from anthropic import Anthropic

client = Anthropic()
SYSTEM = "You write concise release notes for a developer audience."

def turn(history, user_text, model="claude-haiku-4-5"):
    history.append({"role": "user", "content": user_text})
    resp = client.messages.create(
        model=model, max_tokens=600, system=SYSTEM, messages=history,
    )
    text = "".join(b.text for b in resp.content if b.type == "text")
    history.append({"role": "assistant", "content": text})
    return text, resp.usage

history = []
print(turn(history, "Draft notes for: 'feat: CSV export', 'fix: retry on 429'")[0])
print(turn(history, "Shorten it to three bullets.")[0])
print("turns:", len(history), "| last input tokens:", turn(history, "Add a heading.")[1].input_tokens)

Watch input_tokens climb on each turn. That growth is the reason context management is its own exam domain rather than an afterthought.

Two constraints to know. Messages must alternate user and assistant. And you may end the list with a partial assistant message to constrain the opening of the reply:

messages=[
    {"role": "user", "content": "List the three changes as JSON."},
    {"role": "assistant", "content": "["},      # prefill: the reply continues from here
]
Exam lens

Statelessness drives several answers. "Conversation history is growing past the context window" is solved by summarising or dropping older turns, not by a larger max_tokens. "Responses drift from the required format over a long chat" points at the system prompt, which applies to every turn, rather than at repeating instructions in each user message. And assistant prefill is the cheapest way to force a reply to start in a given shape.

3

Stream, and handle what streaming breaks

Code. Latency is a design decision, not a detail.

A long response that arrives all at once feels broken. Streaming sends tokens as they are produced, which changes perceived latency without changing cost.

with client.messages.stream(
    model="claude-haiku-4-5",
    max_tokens=600,
    system=SYSTEM,
    messages=[{"role": "user", "content": "Write release notes for 12 merged PRs..."}],
) as stream:
    for chunk in stream.text_stream:
        print(chunk, end="", flush=True)

    final = stream.get_final_message()   # full message once the stream ends
print("\n", final.stop_reason, final.usage)

Streaming complicates three things worth knowing before you reach for it: you cannot validate the whole output until it is finished, so schema checks happen at the end; an error can arrive mid-stream after you have already shown text to the user; and time-to-first-token, not total duration, is the number that matters to the person waiting.

Long requests

Very long non-streaming requests can hit a timeout at the network layer before the model finishes. If a large max_tokens request fails with a timeout, streaming is the fix rather than a longer client timeout.

Exam lens

Distinguish the two latency levers. Streaming changes when the user sees the first token; it does not reduce total generation time or cost. Reducing max_tokens, shortening the prompt, or moving to a smaller model changes the actual work. A scenario complaining that "users think the app has frozen" wants streaming; one complaining that "responses take too long and cost too much" wants a model or prompt change.

4

Force output into a shape you can parse

Code. Asking politely for JSON is not a contract.

Prompting for JSON usually works and occasionally does not, and the failure lands in production at 2am. Defining a tool with an input schema and requiring its use turns the format into a constraint the API enforces.

structured.py

RELEASE_NOTE_TOOL = {
    "name": "emit_release_notes",
    "description": "Return structured release notes for a set of merged pull requests.",
    "input_schema": {
        "type": "object",
        "properties": {
            "headline": {"type": "string", "description": "One line, under 60 characters"},
            "highlights": {
                "type": "array",
                "items": {
                    "type": "object",
                    "properties": {
                        "title": {"type": "string"},
                        "category": {"type": "string", "enum": ["feature", "fix", "chore"]},
                        "breaking": {"type": "boolean"},
                    },
                    "required": ["title", "category", "breaking"],
                },
            },
        },
        "required": ["headline", "highlights"],
    },
}

resp = client.messages.create(
    model="claude-haiku-4-5",
    max_tokens=800,
    system=SYSTEM,
    tools=[RELEASE_NOTE_TOOL],
    tool_choice={"type": "tool", "name": "emit_release_notes"},   # must use this tool
    messages=[{"role": "user", "content": PR_TITLES}],
)

notes = next(b.input for b in resp.content if b.type == "tool_use")
print(notes["headline"], len(notes["highlights"]))

Note what changed. stop_reason is now tool_use, the payload arrives in a tool_use block's input field already parsed as an object, and there is no JSON string to clean up. The "tool" here executes nothing — it exists purely to describe a shape.

Descriptions inside the schema are read by the model. "One line, under 60 characters" does more work than any instruction in the system prompt.

Exam lens

Rank the three approaches to structured output. Prompt-only JSON is the weakest and needs defensive parsing. Assistant prefill with [ or { is stronger and free. A tool schema with tool_choice forcing it is strongest, and is the expected answer whenever a scenario says the output feeds another system. Watch for the distractor that reaches for a larger model to fix malformed JSON, which treats a design problem as a capability problem.

5

Count tokens and cut the bill

Code. Cost is a first-class engineering property here.

Measure before optimising. The API can count tokens for a request without running it:

count = client.messages.count_tokens(
    model="claude-haiku-4-5", system=SYSTEM,
    messages=[{"role": "user", "content": PR_TITLES}],
)
print(count.input_tokens)

Now apply prompt caching. If a long, stable prefix — a style guide, schema documentation, examples — repeats across calls, mark the end of it and subsequent calls reuse the processed prefix at a reduced rate:

system=[
    {"type": "text", "text": SYSTEM},
    {"type": "text", "text": STYLE_GUIDE,           # long and unchanging
     "cache_control": {"type": "ephemeral"}},
]

Then read usage.cache_creation_input_tokens on the first call and usage.cache_read_input_tokens on the second. If the second is zero, the prefix was below the minimum cacheable length or the cache had expired.

LeverWhat it changesReach for it when
Prompt cachingCheaper reuse of a stable prefixThe same long context repeats across calls
Batch APISubstantially lower rate, asynchronousLatency does not matter — backfills, bulk jobs
Smaller modelLower rate and fasterThe task is classification, extraction or routing
Shorter contextFewer input tokens on every callAlmost always the first thing to try
Lower max_tokensCaps output cost and truncation riskOutput length is predictable
Verify

Cacheable minimum lengths, cache lifetime and batch discount all change. Confirm current figures in the docs before quoting them to anyone.

Exam lens

Read the constraint in the question. "Reduce cost without changing latency" rules out the Batch API. "Cut cost for an overnight job" rules it in. "The same 20-page policy is sent with every request" is caching. And know that caching bills the first call slightly higher to write the cache, so it pays off across repeated calls rather than on one.

Choose a model with evidence

Code. Replace habit with a small experiment.

Run the same task across the model tiers and record quality, latency and cost. Twenty PR-title sets are enough to see a pattern.

compare.py

import time

MODELS = ["claude-haiku-4-5", "claude-sonnet-5"]   # confirm current IDs

for model in MODELS:
    t0 = time.time()
    resp = client.messages.create(
        model=model, max_tokens=800, system=SYSTEM,
        tools=[RELEASE_NOTE_TOOL], tool_choice={"type": "tool", "name": "emit_release_notes"},
        messages=[{"role": "user", "content": PR_TITLES}],
    )
    out = next(b.input for b in resp.content if b.type == "tool_use")
    print(f"{model:24} {time.time()-t0:5.2f}s  "
          f"in={resp.usage.input_tokens:5}  out={resp.usage.output_tokens:5}  "
          f"items={len(out['highlights'])}")

For a schema-constrained summarisation task, the smaller model usually holds up, and that is the point. The tiers differ most on multi-step reasoning, ambiguity and long-context synthesis — not on formatting work you have already constrained.

Where a task genuinely needs deliberation, extended thinking gives the model room to reason before answering, at the cost of the thinking tokens:

resp = client.messages.create(
    model="claude-sonnet-5", max_tokens=4000,
    thinking={"type": "enabled", "budget_tokens": 2000},
    messages=[{"role": "user", "content": "Which of these 40 changes are breaking, and why?"}],
)
answer = "".join(b.text for b in resp.content if b.type == "text")

The response now contains thinking blocks alongside text blocks, which is the second time in this lab that content[0].text would have been wrong.

Exam lens

Model-selection questions describe a workload and expect a tier. High volume, simple, latency-sensitive classification points at the smallest model. Multi-step reasoning over ambiguous input points higher. A mixed workload points at routing — a cheap model first, escalating only when it is uncertain. Extended thinking is for genuine reasoning depth, not for making short answers better, and its budget comes out of max_tokens.

Handle failure like production

Code. The difference between a demo and an application.

Everything so far assumed success. Now handle the four failures that actually occur.

import anthropic, time, random

def call_with_retry(**kwargs):
    for attempt in range(5):
        try:
            return client.messages.create(**kwargs)
        except anthropic.RateLimitError:                 # 429
            wait = (2 ** attempt) + random.random()
        except anthropic.APIStatusError as e:            # 5xx, including overloaded
            if e.status_code < 500:
                raise                                    # 4xx: your bug, do not retry
            wait = (2 ** attempt) + random.random()
        except anthropic.APIConnectionError:             # network
            wait = (2 ** attempt) + random.random()
        print(f"retry {attempt+1} in {wait:.1f}s")
        time.sleep(wait)
    raise RuntimeError("exhausted retries")
FailureRight response
429 rate limitExponential backoff with jitter; respect retry headers; consider batching
529 overloadedBackoff and retry — transient, not your fault
400 invalid requestNever retry. Fix the request: missing max_tokens, bad role order, oversized context
401 authenticationNever retry. The key is wrong, missing or revoked
stop_reason == "max_tokens"Not an exception at all. Output was truncated; raise the cap or shorten the task

The SDK retries some of this for you — Anthropic(max_retries=3) — but writing it once teaches which classes are retryable, which is what gets tested.

Keys

Never ship a key to a browser or mobile client. Anything the user's device holds, the user holds. Calls go through your backend, which holds the key in an environment variable or a secret manager and rotates it on a schedule. A key committed to git is compromised even after you delete the commit.

Exam lens

The retryable/non-retryable split is the testable idea: 429 and 5xx yes, 4xx no. A scenario where retries make things worse is describing a client hammering a 400. Separately, know that a truncated response is a stop reason rather than an error, so it will never appear in your exception handler — code that only catches exceptions ships silently truncated output.
